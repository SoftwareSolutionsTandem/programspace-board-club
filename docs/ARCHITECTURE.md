# Архитектура

Статус: **согласована как предварительная, под вертикальный срез**; параметры уточняются измерениями (этап 1c). Абстракции появляются только тогда, когда их требует реальная задача. Например, общий интерфейс игрового модуля оформляется, когда начнётся вторая игра.

## 1. Стек (предварительный, уточняется прототипом)
| Слой | Выбор | Почему | Что проверяем прототипом |
|---|---|---|---|
| Язык и сборка | TypeScript (strict) + Vite | быстрая разработка, статическая сборка в zip для Яндекс Игр | размер бандла, время старта |
| Сцена партии | PixiJS v8 | WebGL-рендер, хорошо держит анимацию персонажа и карт на телефонах, MIT | FPS и время кадра на слабом Android, память текстур |
| Экраны и меню | HTML/CSS поверх сцены | чёткий текст, вёрстка, доступность, i18n | безопасные зоны, поворот экрана |
| Анимации | свой небольшой модуль твинов на тикере Pixi | без лишней зависимости | хватит ли его для эмоций персонажа |
| Аудио | своя тонкая обёртка над Web Audio API | шины, приоритеты и приглушение пишем сами | задержка, декодирование, iOS |
| Тесты | Vitest; Playwright для e2e в браузере (production-сборка, компьютер и телефон) | чистые функции правил тестируются без браузера | — |

Новые зависимости — только с проверкой лицензии и записью в `DECISIONS.md`.

## 3. Поток данных в партии
```
ввод (указатель, касание, клавиатура) → намерения игрока / ход ИИ
        │ Action
        ▼
rules.apply(state, action) ──► новое состояние + [доменные события]
        │                                  │
        │ projectView(seat)                ├──► scene: анимация карт
        ▼                                  ├──► director: эмоция + заявка в VoiceChannel
     ИИ.decide(view)                       └──► ui: HUD, кнопки, результат
```
- Правила ничего не знают о сцене, звуке и платформе.
- Сцена может «проигрывать» события с задержкой (анимация), но состояние истины — в правилах. Ввод блокируется, пока анимация ключевого события не завершена.
- Ход ИИ запрашивается контроллером после анимаций. Время раздумья добавляется для драматургии и на решение не влияет.

## 3а. Адаптивная компоновка (телефон и компьютер)
Полная спецификация — `docs/LAYOUT.md`. Коротко:
- Две основные компоновки — `portrait` (телефон) и `landscape` (компьютер) — плюс промежуточные `portrait-wide` и `landscape-compact`. Расположение зон перестраивается, а не масштабируется.
- **Не зависят от экрана и способа ввода:** правила, ИИ, состояние партии, контроллер, режиссёр реакций, аудиосистема. Размеры экрана в них не передаются.
- `computeLayout(viewport) → LayoutSpec` — единственный источник геометрии. Pixi-сцена раскладывает объекты по нему, HTML-интерфейс получает те же прямоугольники через CSS-переменные.
- Ресайз и поворот: `ResizeObserver` + `visualViewport`, пересчёт не чаще одного раза за кадр. Объекты переезжают к новым целям анимацией, состояние партии и звучащая реплика не прерываются.
- Ввод: указатель, касание и клавиатура превращаются в одни и те же намерения (`selectCard`, `playSelected`, `take`, `pass`, `pause`, `toggleSound`). Контроллер принимает только намерения.
- Текущий каркас (этап 1.1) пока раскладывает сукно одинаково для всех экранов. `computeLayout` появится вместе со сценой партии.

## 5. Сохранения
- Формат `{ version, settings, progress }`, где `settings` — громкости и «без звука», `progress` — серии и статистика.
- `version` растёт при каждом изменении структуры. Миграции хранятся цепочкой `vN → vN+1`.
- Повреждённые или неизвестные данные → безопасное начальное состояние + запись в журнал. Игра стартует и без сохранений.
- Локально — `localStorage` через адаптер. Облако Яндекса — на этапе 6, через тот же интерфейс.

## 6. Производительность (гипотезы, подтверждаются измерением)
- Цели (проверяются на прототипе, затем фиксируются):
  - 60 FPS на десктопе;
  - стабильные 60 FPS (минимум 30) на Android среднего уровня;
  - время кадра в отладочной панели.
- Стартовая загрузка: только ядро и ассеты Агаты. Остальные персонажи догружаются лениво.
- Векторные слои персонажа при загрузке растеризуются в текстуры нужного разрешения (с учётом devicePixelRatio).

## 8. Продукты: пять сборок из одного `main` (D40)
Для Яндекс Игр планируются пять самостоятельных продуктов: «Дурак», «Шахматы», «Шашки», «Домино» и сборник «Игротека». Все они живут в одной ветке `main` и отличаются только конфигурацией сборки. Долгоживущих веток вида `game/*` нет. Наличие сборки ещё не означает готовность продукта: продукт готов после зелёного CI своей конфигурации и приёмки владельцем.

### 8.1 Конфиг продукта
`src/products/<id>.json`, тип и проверка — `src/products/types.ts`:

| Поле | Назначение |
|---|---|
| `id`, `version` | имя сборки и версия выпуска продукта |
| `strings` | строки, которыми продукт заменяет общий словарь `ru.json`, например `app.title`, `start.subtitle` |
| `storageKey` | ключ настроек в браузере. У «Игротеки» — `igroteka.settings`; **не менять**, иначе игроки потеряют настройки |
| `games`, `characters` | папки `src/games/<id>` и `src/characters/<id>`, которые входят в продукт |
| `publicAssets` | пути внутри `public/`, которые копируются в сборку |
| `icon` | иконка и её статус: `current` — действующая, `temporary` — временная до утверждения, `final` — утверждённая |

Сейчас продуктов три:
- `igroteka`: дурак с Агатой и домино с Дедом Матвеем; словарь без замен, ключ настроек прежний;
- `durak`: своё название и подзаголовок, ключ `durak.settings`, **временная** иконка — та же, что у «Игротеки»;
- `dominoes`: своё название и подзаголовок, ключ `dominoes.settings`, **временная** иконка. Голос Матвея войдёт в `publicAssets` после одобрения владельцем.

Игровые модули продукта перечислены в `src/products/<id>.games.ts` (псевдоним `@product-games`): в бандл попадают только они. Тест сверяет этот список с полем `games` конфига.

### 8.2 Как устроена сборка
- `vite build --mode <id>` выбирает продукт. Обычные режимы (`production`, `development`, `test`) — это «Игротека».
- Псевдоним `@product` указывает на `src/products/<id>.json`. Игра читает его через `src/products/current.ts`, поэтому в бандл попадает конфиг только своего продукта.
- Vite по умолчанию копирует весь `public/` — это отключено (`build.copyPublicDir: false`). Плагин `productPlugin` в `vite.config.ts` выпускает только `publicAssets` и иконку продукта. В режиме разработки `public/` раздаётся целиком.
- Результат: `dist/<id>/`. Рядом лежит отчёт сборщика `dist/<id>.build.json`: какие модули реально вошли в каждый чанк и какие файлы выпущены.

### 8.3 Проверка состава — `npm run check:bundle`
`tools/check-bundle.mjs` (правила — `tools/bundle-audit.mjs`, тесты — `tests/build/bundleAudit.test.ts`) сверяет отчёт сборщика и фактическое содержимое `dist/<id>/`. Текст минифицированного кода не анализируется. Сборка не проходит, если:
- в чанках есть модуль чужой игры, чужого персонажа или конфиг другого продукта;
- игры или персонажа продукта нет в сборке;
- в папке есть файл, не выпущенный сборщиком, или пропал выпущенный;
- ресурс из `public/` лежит вне `publicAssets`, отличается побайтно от исходника или не попал в сборку;
- у файла голоса нет строки в `assets/audio/LICENSES.md` или манифест голоса ссылается на отсутствующий файл;
- иконка или заголовок страницы не совпадают с конфигом.

Временная иконка выводится предупреждением.

До сборки то же проверяет граф исходников — `tests/build/imports.test.ts` (входит в `npm test`):
- от `src/main.ts` с псевдонимами каждого продукта статически достижимы только его игры и персонажи (импорты типов тоже считаются; `src/dev/` — только через `import()` в режиме разработки);
- «Домино» и «Дурак» не делят ни одного модуля игр и персонажей;
- общие модули (`app`, `ui`, `audio`, `core`, `puppet`, `render`, `layout`, `storage`, `i18n`, файлы верхнего уровня `characters/`) не импортируют игры и конкретных персонажей;
- игра не импортирует другую игру, персонаж — игру или другого персонажа;
- правила, ИИ, вид и контроллер матча (`rules/`, `ai/`, `match.ts`, `sim.ts`, `view.ts`) зависят только от своей игры и `core/rng` — анимация и звук на них повлиять не могут;
- проверка сама проверена: синтетическое нарушение (чужой персонаж, чужая игра, `src/dev`) обнаруживается.

### 8.5 Как добавить шахматы, шашки и домино
Для каждой игры — отдельный PR в `main`:
1. Правила, ИИ, сцена и тесты — в `src/games/<игра>/` и `tests/games/<игра>/`, по образцу дурака. Персонаж — в `src/characters/<имя>/`, голос — в `public/audio/ru/<имя>/` с правами.
2. При второй игре вводится общий интерфейс игрового модуля (§1). Контроллер партии дурака (`src/app/session.ts`) переезжает в `src/games/durak/`. Общие `app.ts`, `screens.ts` и `rig.ts` перестают импортировать дурака и Агату напрямую — их выбирает продукт. У сборника появляется экран выбора игры.
3. Конфиг `src/products/<игра>.json` с собственным ключом настроек; в `igroteka.json` игра добавляется в `games`, персонаж — в `characters`.
4. Скрипты `dev:`, `build:`, `preview:` для нового продукта; добавить его в `build:all` и `check:bundle`; добавить проекты и сервер в `playwright.config.ts`.
5. Проверка состава автоматически не пустит игру в чужие сборки.

### 8.6 Игровой модуль (`src/app/game.ts`, 2026-10-20)
Приложение ведёт клуб, выбор соперника, загрузку, настройки и ресайз; партию целиком ведёт модуль игры. Модуль отдаёт:
- персонажа: рисунок по контракту `CharacterArt` (`src/characters/art.ts`), каталог реплик, ключи имени и описания, флаг знакомства в настройках;
- компоновку `layout(viewport)` и разрешения текстур под неё;
- сборку текстур `buildAssets` (приложение хранит их по играм и освобождает через `destroy`);
- сеанс партии `createSession(host, options)` с методами `setAssets`, `setLayout`, `start`, `update`, `onKey`, `setPaused`, `dispose`, `debug`;
- ключи строк клуба, загрузки и правил, ключ «обучение пройдено» и seed обучающей раздачи.

Риг (`src/characters/rig.ts`) и текстуры персонажа (`src/characters/textures.ts`) работают только через `CharacterArt` и не импортируют ни одного персонажа. Фон клуба (`src/render/cafe.ts`) и стол (`src/render/table.ts`) общие для всех игр. Голоса всех персонажей продукта загружаются одним `AudioEngine` из `audio/ru/<персонаж>/manifest.json`.
